## 目标

给 `prompt_templates` 加三个字段，让指令能按产品 / 场景分层，并区分官方与客户模板。这是指令选择器（B-02）的前置。

## 改动

**迁移** `a1b2c3d4e5f6_add_prompt_product_scene_official.py`：

- `product_id` → `products.id`（可空）
- `scene_id` → `asset_scenes.id`（可空）
- `is_official` 布尔，默认 false
- 三个索引

复用阶段 A 已建好的 `products` 和 `asset_scenes` 表，**与图片素材共用同一套产品 / 场景实体**——这样选图和选指令的分类口径一致。

**模型** `backend/app/models/prompt_library.py` 加对应字段。

**接口** `backend/app/api/prompt_library.py`：

- `PromptPayload` 增 `product_id` / `scene_id`
- 创建与更新时校验产品 / 场景归属（跨用户引用返回 404）
- `_item()` 输出三个新字段
- 列表增 `product_id` / `scene_id` / `is_official` 筛选
- **改正文即置 `is_official = false`**，落实总纲第八节「客户模板永不被升级覆盖」；仅改名不影响

## 两个坑

**一、SQLite 下 `batch_alter_table` 会重建表，被外键挡住。**

首次迁移失败：`IntegrityError: FOREIGN KEY constraint failed / DROP TABLE prompt_templates`。原因是 `prompt_versions` 和 `prompt_usages` 都有外键指向 `prompt_templates`，batch 模式的「重建表」策略需要先 DROP，被拒。

事务完整回滚，库未受损（版本仍 `f41a0e9d2c73`，数据零丢失，`integrity_check` 与 `foreign_key_check` 均通过）。

改用原生 `op.add_column`（SQLite 原生支持 ALTER TABLE ADD COLUMN，不重建表）。外键约束在 SQLite 上无法事后添加，故按方言分开：仅非 SQLite 建外键，模型层的 `ForeignKey` 仍提供 ORM 行为。

**二、`in_([None, x])` 匹配不到 NULL。**

我最初写 `product_id.in_([None, product_id])` 想包含未绑定的通用指令，测试直接抓出来——SQL 里 `IN (NULL, 1)` 永远匹配不到 NULL 行。改成 `or_(col.is_(None), col == x)`。

**同一 bug 在既有代码里也存在**：第 131 行 `platform_account_id.in_([None, account_id])`，意图是包含未绑定账号的指令，实际一条也带不回来。属既有行为，按「不中途转向」原则未在本单修改，登记为 BUG-11。

`scenes_json`（自由文本场景名，供 `/recommend/match` 宽松匹配）与新的 `scene_id` 是两个概念，并存不冲突，已在模型加注释说明。
