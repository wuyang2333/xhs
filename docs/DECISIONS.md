## 2026-08-06 · 手机 UI 自动化：长列表必须滚动查找

**现象**：用户测发布时报 `Cannot find the dedicated CodexXHS image album`，但相册肉眼可见就在列表下方。

**根因**：`uiautomator` 只导出已渲染的节点。RecyclerView 里屏幕外的行根本不在 UI 树中，所以 `find_node()` dump 一次就判定「不存在」。

**处理**：新增 `scroll_to_find_node()`——先查当前屏，未命中则按可滚动容器的 bounds 计算滑动距离（不写死像素，兼容不同屏幕尺寸），逐屏查找；列表不再变化即判定到底并停止，不白滚满次数。失败时把当前可见文本一并报出，便于定位。配 5 个测试。

已写进 `CLAUDE.md` 作为常驻规则：**凡在可滚动列表中查找，一律用 `scroll_to_find_node()`**。

**同类风险**：`attach_product()` 找「添加组件」入口和商品结果时仍是裸 `find_node()`（BUG-14）。未一并修改——用户正在测发布，不在这时候动发布路径。

## 2026-08-06 · 指令改为单选直用，推翻总纲第八节的分层组合

**决策**：选一条指令就**完全按它执行**，不做分层叠加。用户也可以直接自己填。两个来源等价。

**理由**：用户明确要求「必须按照我的指令库的指令生成，或则我填写都可以」，并点明「而不是叠加」「不希望他按照自己的指令」。

这与总纲第八节写的「全局基础 + 平台 + 账号 + 产品 + 场景 + 临时补充 = 最终执行指令」相反。B-02 按总纲实现了六层组合，B-03 推翻重做。**以用户当面的要求为准，总纲那一节视为过期。**

**连带发现并修掉的问题**：`ai_service.py` 五个方法各自带一段写死的 `system_prompt`（如「你是小红书内容运营编辑…」），未填要求时还会补「提升表达、增强小红书语感」。所以即使用户选了自己的指令，模型收到的仍是系统那套话垫在前面——直接违反用户要求。现改为用户指定时**整体取代**默认人设，并抑制默认要求文案。

**保留的两条系统约束**（已向用户说明）：生文的「标题：/正文：」输出格式、标题 20 字上限。前者是解析标题与正文的前提，后者是平台硬限制且代码本有兜底截断。它们管「能不能被正确读出来」，不是风格偏好。

## 2026-08-06 · 图片存储统一到素材库（A-06）+ 修掉测试污染真实目录

**背景**：用户浏览器验证时发现草稿工坊选图器几乎是空的。查明系统里并存三套互不相通的图片存储：`media_assets`（3 条）、`ai_generated_assets`（33 条）、磁盘 `storage/media/`（201 个 `xhs-upload-` 文件，**连数据库记录都没有**，靠扫目录列出）。

**决策**：以 `media_assets` 为唯一素材库。AI 生图同时写入（三处落库点全部接上），已有资产一次性回填，两处旧「从图片工坊添加」弹窗换成统一选图器。

`ai_generated_assets` 保留不删——它承载 prompt / model_name / params 等生成元数据，`media_assets` 没有这些字段。两套通过文件路径关联。

**回填结果**：AI 33 + 上传 201 = 新增 231，`media_assets` 共 234 条。脚本幂等（复用 `register_media_asset` 已有的按 `local_path` / `url` 去重），重复运行三次新增均为 0，无重复记录。

**顺带修掉 BUG-09（测试污染真实数据）**：`storage_dir` 原本写死为 `Path("backend/app/storage")`，测试无法覆盖，导致两个走 `generate-cover` 的测试**每跑一次全量测试就往用户真实媒体目录写 2 个图片文件**。基线那几轮一直在漏。

处理：`storage_dir` 改为可被 `STORAGE_DIR` 环境变量覆盖（默认值不变，生产行为不变），新增 `tests/conftest.py` 在任何 backend 模块导入前把它指向临时目录。`test_api.py` 在模块级就构造了 `TestClient(app)`，届时 `get_settings()` 已缓存，所以 conftest 是唯一可靠的注入点。

配 `test_tests_never_write_into_the_real_storage_directory` 守住，验证泄漏从 2 降到 0。

## 2026-08-06 · alembic.ini 指向错误的数据库（执行 A-01 时发现）

**现象**：`backend/alembic.ini` 第 3 行写死 `sqlalchemy.url = sqlite:///./backend/app/storage/spider_xhs.db`，而应用实际使用 `./data/spider_xhs.db`（`config/default.yaml` 的 `sqlite_path`）。

直接 `alembic upgrade head` 会在 `backend/app/storage/` 新建一个空库、把全部 20 个迁移跑进去，**真实库完全没动，且命令输出看起来完全正常**。执行 A-01 时确实踩了这一脚——从输出里 4 个迁移全跑（而真实库应只差 1 个）才发现不对。

**这解释了真实库为何落后一个迁移**：之前的迁移是通过别的途径（环境变量或应用自身初始化）应用的，而不是这个默认配置。

**处理**：已在 `CLAUDE.md` 顶部加门禁，要求跑迁移必须显式带 `DATABASE_URL`，且跑完要核对 `alembic_version` 与实际表结构，不能只看命令输出。

**未修根因**：`alembic.ini` 的默认值本身还是错的。改它属于配置变更，留待单独处理（已记入 `STATE.md` 已知问题 BUG-05）。

## 2026-08-05 · 设备助手：Windows + 本机 Mac 一体机，**仅 USB**

**决策**：设备助手做 Windows 和 Mac 两个版本，**第一版只支持 USB，不做无线**。

目标机器只有两台：用户当前使用的 Mac 一体机（USB 实测可用）、以后的 Windows（最终设备形态）。同事的 Mac mini 排除在范围外——那台 USB 授权弹窗多种手段均无法唤出，是唯一逼出无线需求的机器，用户明确不再处理它。

**砍掉无线消除的问题：**

- IP 变化导致绑定失效 / 发错设备——USB 不使用 IP
- 「多台手机同一 IP」的担忧——不存在（实为端口 `5555` 相同，那是无线调试固定端口；同一 wifi 内 IP 不会重复，否则会冲突）
- 无线调试对整个局域网开放、无需认证即可操作手机的安全隐患
- 跨电脑抢占同一手机——USB 物理独占，线只能插一台

**当前代码在纯 USB 下已经安全。** `android_xhs_service.py` 每个 adb 调用都带 `-s <目标>` 指定设备，且 USB 下该地址即手机硬件序列号，故「多手机不会路由到错误设备」已成立，无需额外改造。

**硬件序列号核对（`ro.serialno`）降级为非必需**：它是为无线场景准备的防护。若将来恢复无线支持，必须先补上——规则是绑定记序列号、IP/端口视为临时通道信息、每次操作前核对且不符即中止。

**无线状态**：不删除、不实施，留作后续需要时再开。

**决策**：一台手机连在哪台电脑上就由哪台使用，不实现跨电脑的抢占协议。

## 待议

### 两个比总纲第十六节更要紧的问题

**1. 租户模型：现在的 `user_id` 代表一家公司还是一个员工？**

全库无 `tenant_id`，阶段 A 已落地的 6 张素材表全部只有 `user_id`。若 `user_id` 事实上等于「一家公司」，阶段 D 的工作不是加列，而是把 user 拆成 tenant + user 两层——要逐条决定已有数据归属哪个租户，代价远高于加列。

唯一约束也受影响：现在是 `(user_id, name)`，加租户后要变成 `(tenant_id, user_id, name)` 还是 `(tenant_id, name)`，取决于「同公司不同员工能否建同名文件夹」。

建议：现在就定，并尽早加一个可空 `tenant_id`。空列成本近零，回头补列的成本随表数量和数据量增长。

**2. 设备助手的认证方式未定**（部分已解决）

序列号核对已定（见上方决策），解决了「发错手机」。仍未定的是**服务端与助手之间如何互认**：配对密钥如何下发与轮换、任务是否签名（防重放与篡改）、助手如何确认任务来自本公司服务端。

自用阶段可延后；对外交付前必须解决——这是全系统风险最高的组件，能往真实账号发不可撤回的内容。

无线调试对整个局域网开放（无需认证即可操作手机）这一点同属此列。ADB 授权私钥的本地保护方式也未写。

### 待定的实现细节

- **图片张数校验的机制未定。** 总纲第七节第 7 步要求核对任务图片数与手机实际选中数，但未规定如何计数。建议解析 UI 层级而非图像识别，并规定解析失败必须中止。配套的「手机适配规则」格式（小红书版本 → 选择器集合）也未定义。
- **官方模板与客户模板缺标记位。** `prompt_templates` 现有 `source_type`（默认 `"manual"`）、`source_ref`、`source_hash`，但无显式官方标记。升级流程无法判断哪条可覆盖。建议加 `is_official`，客户复制官方模板后副本置 false。
- **挂车按名称匹配过脆。** 商品名会截断、会重名。系统已存产品编号，若小红书支持按编号搜应优先用编号。「精确匹配」的判定标准（是否允许空格差异）也要写清。
- **崩溃回滚应从备份恢复，不跑 downgrade。** 迁移中途失败时 schema 处于半应用状态，反向迁移不可靠。`downgrade()` 是给正常回退用的。
- **「确认已发布」应是独立权限。** 总纲第十二节的「待核实」锁定机制，若发布权限即可解锁，低权限用户清锁会导致重复发布。
- **重启后在途任务未定义。** 状态为 `publishing` 的任务在服务端重启后应一律标为「待核实」，不可自动重试（会重复发布）。
- **缺规模阈值与离场条款。** 单文件夹图片上限、单公司手机数、并发任务数均无量级判断；授权到期后客户数据能否全量导出未定（商务 + 合规问题，建议随计费方式一起定）。

### 总纲第十六节 7 问的现状

已关闭：企业服务端优先平台（Windows + Mac）、首批外部图片同步来源（不做同步）。

仍阻塞阶段 D：**计费方式**（与租户模型绑定）、客户能否关闭中央健康监控。

影响阶段 C 可延后：商品库手工维护还是从手机同步。

可最后答（建议合并为一条）：客户服务端是否仅限局域网、是否支持跨地点办公。

## 2026-08-05 · 流程简化为三步

**决策**：讨论 → 登记 → 派单。去掉封板和 review 两个独立阶段。

**理由**：用户不是程序员，六步流程的仪式成本超过收益。被去掉的两步，其有价值的部分保留在别处：

- 封板原本要保证「实施前把要做的写清楚」→ 并入登记，规格文件照常写，但不冻结、不记版本、可随时改
- review 原本要保证「做完的东西真的对」→ 其中机械可查的部分（测试、构建、无残留）已在收尾门禁里；派出去的单回来由主会话核对验收项

**保留收尾门禁的理由**：TS2440 那次构建失败正是收尾没跑检查导致的，代价是一整轮排查。门禁由主会话执行，不需要用户参与，不增加其负担。

## 2026-08-05 · 文档体系落地

**决策**：采用 `CLAUDE.md` + `docs/{STATE,DECISIONS}.md` + `docs/{specs,tickets}/` 四件套。

**理由**：项目真实开发形态是「多 AI 工具轮换 + 随时断线 + 无 git 历史」，文档首要目标是让新会话五分钟内接手，不是规范流程。初版按流程阶段建了 6 个目录，属过度设计，砍半。

关键取舍：

- 讨论稿与封板规格**不分目录**，同一文件靠 `状态:` 字段流转。分开会在封板时产生一次内容复制，那是漂移的入口。
- 常驻规则放**仓库根 `CLAUDE.md`** 而非 `docs/`。这些是给 AI 会话的指令，Claude Code 启动时自动加载；放 docs 深处可能根本不被读到。「测试不得触发真实发布」是不可逆红线，不能靠「希望对方读到某个文档」来保证。
- 验收对照表长在规格里，不单开 `testing/`。验收标准与测试名挨着写，空格即缺口。
- bug 不单开 `BUGS.md`。要修的 bug 就是派单，两处登记必然对不上。`STATE.md` 只挂索引行，修完删除，历史留在派单文件。
